# Архітектурні рішення

---

## 1. SaaS-ready з першого дня

**Рішення:** Додаємо таблицю `stores` і колонку `store_id` до всіх основних таблиць з самого початку.

**Чому:** Зараз будуємо один магазин A-green. Але ціль — платформа де кожен власник може відкрити свій магазин (як Shopify). Якщо не закласти `store_id` зараз, при переході на SaaS доведеться переписати 30+ таблиць і всі запити.

**Як працює зараз:** `store_id = 1` скрізь. Laravel Global Scope фільтрує автоматично.

**Перехід до SaaS (Phase 19):** Додати реєстрацію магазинів, білінг, роутинг по доменах — схема БД вже готова.

---

## 2. Окремі _translations таблиці для мультимовності

**Рішення:** Кожна сутність з текстовим контентом має дві таблиці — базову і `_translations`.

**Чому не JSON колонки:** `slug` залежить від мови (`/uk/abrazyvni-materialy` ≠ `/en/abrasive-materials`). JSON не можна ефективно індексувати. MeiliSearch краще індексує окремі рядки.

**Патерн:**
```
categories (id, store_id, image, sort_order, is_active)
category_translations (category_id, locale, name, slug, description, meta_*)
UNIQUE(category_id, locale)
```

**Мови:** uk (default), en, pl — керуються через таблицю `languages` в Filament.

## 3. EAV для атрибутів і фільтрів каталогу

**Рішення:** Атрибути товарів (зернистість, колір, розмір...) зберігаються через EAV — окремі таблиці `attribute_definitions`, `attribute_values`, `product_attribute_values`.

**Чому:** Різні категорії мають абсолютно різні характеристики. Жорстко зашити їх в `products` неможливо — полів сотні і у кожного магазину вони різні.

**Як адмін налаштовує фільтри:**
1. Створює атрибут "Зернистість" (тип: select, фільтрувати: так)
2. Додає значення: P80, P120, P240
3. В категорії "Абразиви" → Фільтри → додає "Зернистість", тип: чекбокси
4. На товарі вибирає: Зернистість = P120

Фронтенд автоматично показує правильні фільтри для кожної категорії.

## 4. Driver Pattern для інтеграцій, доставки та оплати

**Рішення:** Замість хардкоду 1С/НП/LiqPay — таблиці з полем `driver` і JSON `settings`. Кожен driver — PHP клас що реалізує спільний інтерфейс.

**Чому:** Різні клієнти використовують різні ERP (1С, SAP, Excel). Різні служби доставки. Щоб додати нову — створити PHP клас + рядок в БД. Більше нічого.

**Таблиці:**
- `integrations` — ERP/CRM підключення (`driver`: one_c, sap, excel, api)
- `shipping_providers` — доставка (`driver`: nova_poshta, ukrposhta, meest, justin)
- `payment_providers` — оплата (`driver`: liqpay, wayforpay, invoice_vat, postpay)

**Специфічні налаштування** (API ключі, реквізити) — в JSON полі `settings`. Жодного hardcode в коді.
